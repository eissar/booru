Roaring bitmap tag index size estimate

Formula:
size ≈ associations × 2 bytes (worst case) + per-tag overhead
associations = images × average tags per image

Dense chunks (more than 4096 IDs per 65,536-ID chunk) use an 8 KB bitset, which is cheaper than 2 bytes per ID. Clustered IDs compress further with run containers. So 2 bytes per association is an upper bound.

Per-tag overhead is about 50–100 bytes. It is negligible at ~50k tags and dominant at billions of tags.

Examples:

2M images × 25 tags = 50M associations
50M × 2 B = ~100 MB worst case
Realistic: 60–150 MB

50M images × 40 tags = 2B associations
2B × 2 B = ~4 GB worst case
Realistic: 2–4 GB

500M associations × 2 B = ~1 GB

2 billion distinct tags
2B × ~50–100 B overhead = 100–200 GB or more before any data
Unrealistic vocabulary. Real boorus have tens to hundreds of thousands of tags.

Assumptions:
- 25 and 40 tags per image are guesses. Replace them with your real average.
- Size scales with total associations, not with image count or tag count alone.
- These are estimates. Nothing has been benchmarked.

Slug-style tags

Slug-style tagging keeps a strict identifier separate from a free-form display name. The identifier, such as blue-eyes, uses only lowercase letters, digits and hyphens, and it is unique. Search, URLs and the index all use it, so tag lookup is an exact match on an indexed column, with no case-insensitive scans. Search syntax stays simple because identifiers never need quoting or escaping, and characters outside the slug set, like / for folders or : for namespaces, are free to act as operators without colliding with tag names. The display name, such as "Blue eyes" or "AC/DC", can hold any text and is never parsed, so you can rename or localize it without touching tag assignments, links or saved searches. Aliases are alternative display names that resolve to one canonical slug. Distinct meanings require separate tags with distinct slugs.

Rule: ^[a-z0-9]+(-[a-z0-9]+)*$
No leading, trailing or doubled hyphens.
